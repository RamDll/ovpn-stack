# install/ — архитектура установщика и журнал отладки

[`README.md`](README.md) — как запускать: быстрый старт, аргументы, что
делает скрипт. Здесь — как оно устроено, почему именно так, и что
ломалось на живых прогонах. Код пишется по разделам 1–13; находки с
прогонов дописываются под «# Журнал отладки» в конце, сразу под
заголовком (новые — сверху).

---

## Чем отличается от корневого `install.sh`

Это **отдельный установщик**, не связанный с корневым
[`install.sh`](../install.sh):

| | корневой `install.sh` | `install/setup.sh` |
|---|---|---|
| откуда запускается | на сервере (`sudo bash install.sh`) | с домашнего ПК |
| что ставит | OpenVPN + ovpn-admin + nginx | + **VLESS Reality (3x-ui)**; режимы `--vless`/`--openvpn`/`--all` |
| SSH-хардненинг | нет | да (новый порт, ключ, `PermitRootLogin no`, страховочный откат) |
| firewall | правит существующий | свой nftables ruleset |

Оба поддерживаются; корневой проще и «на месте», этот — полный
управляемый прогон с домашней машины. Проверен чистыми прогонами всех
трёх режимов на тестовом сервере (см. журнал ниже).

## Две вещи, на которых сломались первые версии

Полный разбор — §9, §11 и журнал ниже; здесь коротко, чтобы не
наступить снова.

- **Внешний REALITY `dest`.** REALITY синхронно дозванивается до `dest`
  на **каждое** входящее соединение ещё до чтения ClientHello. Внешний
  домен (`www.kth.se`, быстрый и надёжный сам по себе) в этой роли давал
  **0 из 10** успешных хэндшейков подряд — зависание внутри xray без
  единой ошибки в логе. Локальная заглушка на `127.0.0.1:8444` тем же
  прогоном — **10 из 10**. `dest` теперь всегда локальный (§9).
- **Версия 3x-ui / xray-core.** Запинена на v3.4.2 (образ
  `ghcr.io/mhsanaei/3x-ui:v3.4.2`, xray-core 26.6.27). В v3.6.0
  xray 26.7.28 ставит дефолтный `minClientVer` REALITY v26.3.27 и режет
  клиентов со старым ядром, а опустить его 3x-ui не даёт (§11).

Плюс мелочи, всплывшие с реальным телефонным клиентом: `fingerprint`
должен быть `firefox`, не `chrome`; self-signed сертификат заглушки —
с SAN, не только CN. Детали — §9.

## 1. Назначение и сценарий

**Вход:** только что купленный VPS (Debian 13, от 1 ГБ RAM). Провайдер
выдал IP и root-пароль. Больше ничего нет — ни ключей, ни домена.

Диск: `--vless` — ~5 ГБ хватит; `--openvpn`/`--all` — от ~12 ГБ
комфортно, на 10 ГБ впритык. Пик — локальная сборка `ovpn-admin`:
node_modules + vite build + go build + BuildKit-кэш дают 3–4 ГБ, из них
финальный образ ~150 МБ. `build-cache-prune` в конце прогона
(`docker builder prune -af` + `image prune`) возвращает эти 2–4 ГБ;
если диск забьётся раньше, на этом шаге упадёт с `no space left`.

При RAM < ~2 ГБ установщик сам поднимает swap 2 ГБ (нужно ~2.6 ГБ
свободного диска) — иначе та же сборка `ovpn-admin` ловит OOM по
памяти.

**Выход:** настроенный сервер, готовые ключи подключения, файл со сводкой
на домашней машине.

**Запуск:** с домашнего ПК. Одна команда.

- **Linux / macOS** — нужен `bash`, `openssh` (клиент, ≥ 8.4), `openssl`,
  `awk`/`sed`/`coreutils`. Всё это обычно уже стоит. `qrencode` — опц.
  (QR в конце). `sshpass` **не нужен** — root-пароль первого подключения
  скармливается `ssh` через `SSH_ASKPASS` (`SSH_ASKPASS_REQUIRE=force`,
  отсюда требование OpenSSH ≥ 8.4; на более старых — `ssh` спросит
  пароль вручную несколько раз за прогон).
- **Windows 10/11** — через **WSL2**: `wsl --install` (в PowerShell от
  админа) → перезагрузка → в Ubuntu-консоли `git clone` и `./setup.sh`.
  Внутри WSL это обычный Linux, отдельной поддержки не требует. Git Bash
  формально может сработать, но не тестировался.

## 2. Принципы

Эти требования важнее функциональности. Нарушение любого — блокер.

1. **Идемпотентность.** Повторный прогон ничего не ломает и не пересоздаёт
   существующее. Скрипт будет запускаться много раз.
2. **Неразрушающее поведение.** Никаких `rm -rf` по чужим путям, никакого
   сноса существующих установок без явного подтверждения.
3. **Доустанавливаемость.** Поставил только VLESS — через месяц можно
   добавить OpenVPN, не трогая работающее и не перевыпуская ключи.
4. **Проверка перед разрушением.** Всё, что может отрезать доступ к серверу
   (SSH, firewall), делается только после проверки нового пути **отдельным
   новым соединением**.
5. **Никаких вложенных `bash <(curl ...)`.** Всё, что выполняется, лежит
   в этом репозитории или скачивается с проверкой sha256.
6. **Ни одного упоминания конкретного хостинг-провайдера** в коде, конфигах
   и сводке. Провайдер может смениться. Писать нейтрально — «панель
   управления сервером».
7. **Секреты не в git.** Файл сводки — `chmod 600`, вне репозитория,
   в `.gitignore`.

## 3. Структура файлов

```
install/
├── README.md            ← как запускать (быстрый старт, аргументы)
├── NOTES.md             ← этот файл: архитектура, решения, журнал отладки
├── setup.sh             ← единственная точка входа (запуск с домашнего ПК)
├── bootstrap.sh         ← на сервере: шаги 1–3 (система, SSH, firewall)
├── install-vpn.sh       ← на сервере: шаги 4–6 (Docker, сертификат,
│                          сервисы, инбаунд) + сборка сводки
└── templates/
    ├── nftables.conf.tmpl
    ├── nginx.conf.tmpl
    └── docker-compose.yml.tmpl
```

`setup.sh` scp-ит `bootstrap.sh` и `install-vpn.sh` на сервер и дёргает
их подкоманды по SSH; полный репозиторий на сервер попадает отдельно
(`git clone` в `/opt/ovpn-stack` — нужен для `admin/` и шаблонов).
`bootstrap.sh` ничего не знает про VPN — это чистая подготовка любого
Debian-сервера, отделён специально, чтобы переиспользоваться.

## 4. Режимы установки

Спрашивается один раз в начале. Флаги для неинтерактивного прогона:
`--vless`, `--openvpn`, `--all`.

|                     | только VLESS | только OpenVPN | оба      |
|---------------------|--------------|----------------|----------|
| 443/tcp             | 3x-ui        | —              | 3x-ui    |
| UDP-порт            | —            | OpenVPN        | OpenVPN  |
| Панели за nginx     | 3x-ui        | ovpn-admin     | обе      |
| IP-сертификат       | нужен        | нужен          | нужен    |

Nginx и сертификат нужны всегда — панель есть в любом режиме.
Набор правил nftables зависит от режима, поэтому конфиг — шаблон
с подстановкой, а не статический файл.

## 5. Шаг 1 — подготовка системы

**Ввод на домашнем ПК**

| Параметр            | Промпт / дефолт                                       |
|---------------------|------------------------------------------------------|
| режим               | меню `[1-3]`, если не задан `--vless`/`--openvpn`/`--all` |
| IP сервера          | промпт, если не задан `--ip`                          |
| имя пользователя    | промпт с дефолтом `whoami` (текущий юзер домашней машины, нижний регистр; Enter — принять); `--user` переопределяет без вопроса. Это имя **нового** sudo-юзера на сервере, не логин в существующий |
| пароль пользователя | скрытый промпт; **Enter — сгенерировать** (24 симв.); короче 8 симв. → тоже генерируем |
| root-пароль         | скрытый промпт, только при первом подключении; неверный — переспрашивает до 3 раз |
| домен для SNI       | `--sni <domain>`, иначе промпт на «Шаге 5»; **Enter — случайный из встроенного пула** (§9) |

Имя приводится к нижнему регистру и валидируется по `^[a-z_][a-z0-9_-]*$`.
При повторном прогоне имя, пароль, SNI, пути и пароли панелей берутся из
`install/.state/<ip>/state.env`, промпты пропускаются.

**Первое подключение**

- Забрать host key (TOFU), запинить в локальный `known_hosts` проекта,
  отпечаток напечатать в лог. Интерактивной сверки с панелью хостинга
  нет — на практике не сверяли, а шаг путал.
- Вход по root-паролю. Пароль читается один раз скрытым вводом и на время
  первого подключения экспортится в `SSH_ASKPASS`-хелпер
  (`install/.state/<ip>/.askpass`, пароль в файле не лежит) — `ssh`/`scp`
  берут его оттуда без повторных промптов. Снимается из окружения и
  удаляется сразу после заливки ключа.

**На сервере**

1. Свежий VPS в первые минуты держит dpkg-lock под cloud-init /
   `apt-daily` / `unattended-upgrades`. Вместо того чтобы ждать —
   **остановить** их таймеры и юниты (`stop_apt_daily`), потом коротко
   подождать освобождения lock; `apt-get` вдобавок идёт с
   `-o DPkg::Lock::Timeout=300` и тремя ретраями. В конце шага таймеры
   `apt-daily` возвращаются.
2. `DEBIAN_FRONTEND=noninteractive`, `NEEDRESTART_MODE=a` —
   без второго `needrestart` в trixie повесит сессию наглухо.
3. `dpkg --configure -a` (доделать прерванную установку), затем
   `apt update` + `dist-upgrade` с `--force-confold`
4. Доставить, чего нет: **`sudo`, `nftables`, `python3`** — на
   минимальных образах провайдеров их может не быть, а `nftables`
   нужен уже на шаге 3, `python3` — для правки `x-ui.db`
5. При RAM < ~1900 МБ поднять swap 2 ГБ (`/swapfile`) — иначе сборка
   образа `ovpn-admin` (vue-tsc + go build) ловит OOM. На OpenVZ/LXC,
   где `swapon` запрещён, просто пропустить
6. `timedatectl set-timezone Europe/Moscow`, проверить, что
   `systemd-timesyncd` активен и время синхронизировано —
   расхождение ломает TLS-хендшейк Reality
7. `unattended-upgrades`:
   - `/etc/apt/apt.conf.d/20auto-upgrades` класть явно, не полагаться
     на дефолт
   - только security-источник, обычные обновления не включать
   - `Automatic-Reboot "true"`, `Automatic-Reboot-Time "04:00"`,
     `Automatic-Reboot-WithUsers "false"`
   - убедиться, что его таймер не стартовал параллельно с нашим apt
8. Создать пользователя, если его нет. Если есть — не трогать.
   Пароль через stdin или `chpasswd -e`, **не** `useradd -p`
   (иначе виден в `ps`)
9. Добавить в группу `sudo`, **проверить отдельным вызовом**, что sudo
   работает
10. Если обновилось ядро — ребут и ожидание возврата опросом порта

Порядок 4 → 9 обязателен: группы `sudo` может не быть до установки пакета.
Ребут делается здесь, пока парольный вход ещё работает.

## 6. Шаг 2 — SSH

**Ввод:** порт, дефолт — случайный из 20000–60000. Проверить, что
не занят и не 443.

**Порядок операций критичен:**

1. Сгенерировать на домашнем ПК **отдельную** пару ed25519 под этот сервер.
   Не переиспользовать личный ключ. Без пароля на ключ — иначе
   неинтерактивные прогоны сломаются. `chmod 600`, имя с привязкой к IP.
   Если ключ уже есть — переиспользовать, не перезаписывать.
2. Положить публичный в `authorized_keys` пользователя.
   Каталог `700`, файл `600`, владелец — сам пользователь.
   **Дописывать**, а не перезаписывать.
3. **Проверить вход по ключу новым отдельным соединением.**
   Не прошло — остановиться.
4. **Проверить `sudo` из ключевой сессии.** Не прошло — остановиться.
5. Открыть новый порт в nftables **до** перезапуска sshd.
6. Правки sshd — drop-in `/etc/ssh/sshd_config.d/00-ovpn-stack.conf`
   (не основной файл):
   ```
   Port <новый>
   PasswordAuthentication no
   PubkeyAuthentication yes
   PermitRootLogin no
   KbdInteractiveAuthentication no
   ```
   Префикс `00-` обязателен: для `PasswordAuthentication` sshd берёт
   **первое** вхождение, а cloud-init кладёт `50-cloud-init.conf` с
   `PasswordAuthentication yes` — при имени `99-` наш `no` проигрывал и
   вход по паролю оставался живым. Дополнительно скрипт комментирует
   `*Authentication yes` / `PermitRootLogin yes` во всех прочих конфигах
   (`50-cloud-init.conf`, правленый образом провайдера `sshd_config`).
7. `sshd -t` перед рестартом. Не прошло — откат, ничего не перезапускаем.
8. Проверить вход на новом порту новым соединением.
   Старую сессию держать открытой всё это время как страховку.
9. После рестарта — `sshd -T` как авторитетная проверка: если
   `passwordauthentication` всё ещё `yes`, скрипт печатает конкурирующие
   строки, чтобы их было видно в логе прогона.

> **Debian 13, обязательно к учёту.** В trixie sshd по умолчанию
> socket-активирован (`ssh.socket`), и `Port` в `sshd_config` **игнорируется** —
> порт задаётся в юните сокета. Определить, активна ли socket-активация,
> и либо прописать `ListenStream=` через drop-in, либо отключить сокет
> и вернуться на `ssh.service`.

**Пункт 4 — то, что отделяет рабочий скрипт от кирпича.** Если sudo
у нового пользователя не заработал, а root уже закрыт, сервер потерян.

**Пароль пользователю не отключаем** — он нужен для sudo. Это барьер
между «есть ключ» и «есть root».

## 7. Шаг 3 — nftables

Таблица `inet filter`, политика input — `drop`.

Открыть:

- loopback
- established / related
- icmp (иначе ломается MTU discovery)
- SSH-порт из шага 2
- 80/tcp — ACME
- 8443/tcp — nginx с панелями
- 443/tcp — Xray (3x-ui) — **только если режим включает VLESS**
- UDP-порт OpenVPN — **только если режим включает OpenVPN**

Всё остальное — drop. Порты панели и sub-сервера 3x-ui (`XUI_PORT` /
`SUB_PORT`, случайные — см. ниже) наружу **не** открываются, только
`iifname docker0`/`br-*` для nginx-прокси.

**Порядок:** `nft -c -f` (проверка синтаксиса) → применение → проверка
живого соединения. `systemctl enable nftables`, чтобы правила пережили
ночной ребут.

При доустановке режима правила **дополняются**, а не переписываются с нуля.

> **Docker обходит nftables.** Контейнер с `-p 443:443` будет доступен
> снаружи независимо от нашей политики drop — он пишет правила в свои
> цепочки ниже уровнем. Отсюда правило: **всё, что не должно торчать
> наружу, публиковать на `127.0.0.1`**, а не на `0.0.0.0`. Тогда
> конфликтовать не о чем.
>
> По этой же причине **ufw не используем** — поверх Docker он создаёт
> ложное чувство защиты, что хуже его отсутствия.

## 8. Шаг 4 — сервисы

### Раскладка портов

| Порт          | Кто                                    | Наружу |
|---------------|----------------------------------------|--------|
| SSH-порт      | sshd                                   | да |
| 80/tcp        | ACME + редирект                        | да |
| 8443/tcp      | nginx — заглушка + панели              | да |
| 443/tcp       | 3x-ui (Xray, Reality)                  | только режимы с VLESS |
| UDP           | OpenVPN                                | только режимы с OpenVPN |
| 127.0.0.1:8444| fakesite (dest для Reality)            | нет |
| `XUI_PORT` / `SUB_PORT` | панель и sub-сервер 3x-ui (случайные) | нет (docker-only) |

### Сервисы

**3x-ui** — `network_mode: host`.

Обязательно host, по двум причинам сразу:
- в bridge Docker подменяет source-адрес на адрес шлюза, и вся статистика
  по клиентам в панели становится бесполезной;
- панель подставляет в ссылки адрес, который видит у себя — в bridge это
  `172.17.0.x`.

Следствия host-режима:
- секция `ports` не нужна и не работает
- **панель обязана слушать `127.0.0.1`** — в bridge её защищала сеть
  контейнера, в host этого нет
- проверять, что 443 свободен, **до** старта контейнера, иначе получишь
  невнятную ошибку запуска
- внешний IP для ссылок берём из того, что пользователь ввёл в начале
  установки — никаких запросов к внешним сервисам определения адреса

**OpenVPN** — bridge, UDP-порт наружу, volume под PKI.

**nginx** — bridge, порты 80 и 8443, volume под сертификаты и статику.
Поднимается **последним**, когда сертификат уже получен, иначе падает
на отсутствующем файле.

**`ovpn-admin`** собирается локально из `admin/Dockerfile.ovpn-admin`
(Vue-фронт: `npm ci` + `vite build` с `vue-tsc`; Go-бэк: `go build`).
`compose_up_retry` оборачивает `docker compose up -d --build` в 4
попытки с паузой 15с — обрыв pull образов с ghcr.io (часто IPv6) иначе
роняет весь прогон. После того как все контейнеры подняты,
`build-cache-prune` (`docker builder prune -af` + `docker image
prune -f`) чистит BuildKit-кэш этой сборки — 2–4 ГБ, на маленьком
диске половина запаса. Только в режимах с OpenVPN (в `--vless` сборки
нет).

Плашка «СЕРВЕР» в панели ovpn-admin (`sysinfo.go` → `serverName()`)
берёт имя по приоритету: env `OVPN_SERVER_NAME` → файл `/etc/nodename`
→ `os.Hostname()`. Контейнер сидит в `network_mode: "service:openvpn"`
(общий netns, но **свой UTS-namespace**), поэтому `os.Hostname()` = id
контейнера (`73cd2b7f139e`). Compose задаёт `OVPN_SERVER_NAME` =
публичный IP — в панели видно `REDACTED-IP`, а не мусорный id.

### Volume — что нельзя потерять

- **база 3x-ui** (SQLite): все клиенты и статистика
- **приватный ключ Reality**: его потеря убивает все выданные ссылки
- **PKI OpenVPN**

Генерируются один раз. Повторный прогон их **не перезаписывает** —
это самая частая ошибка в подобных скриптах.

### Сертификат

Let's Encrypt выдаёт сертификаты на IP-адреса с 15 января 2026.
Ограничения: обязательно короткоживущие (~6 суток), валидация только
http-01 или tls-alpn-01, DNS-01 не поддерживается.

Домена у нас нет, поэтому это единственный путь к доверенному сертификату.

- 443 занят Xray → валидация только **http-01 через порт 80**
- **Клиент — `acme.sh`**, не Certbot: `--ip-address` в Certbot появился
  только в 5.3, webroot для IP — в 5.4, в Debian почти наверняка версия
  старше. `acme.sh` ставится не через `curl | sh`, а `git clone` на
  пин-тег `3.1.4` (в 3.0.9 ещё нет `--cert-profile`).
- IP-сертификаты у Let's Encrypt обязательно короткоживущие
  (`--cert-profile shortlived`, ~6 суток), поэтому `--days 3` —
  продлеваем, когда осталось меньше 3 суток, дважды в день по таймеру
  с релоадом nginx.
- **Выпуск** — standalone (nginx ещё не поднят, `acme.sh` поднимает свой
  HTTP-сервер через `socat`), порт 80 уже открыт в nftables.
- **Продление** — webroot: через ~6 дней nginx уже держит 80 и
  standalone его не займёт. `cert-switch-to-webroot` переключает режим
  сразу после старта nginx, без переиздания сертификата.
- `--staging` гоняет весь флоу против `letsencrypt_test` (высокие
  лимиты, серт не доверенный браузером) — для повторных тест-прогонов.
  Настоящий rate limit (5 сертов на IP / 168 ч) скрипт ловит и выходит
  с понятным сообщением, не роняя уже сделанное.
- Смена IP убивает сертификат — знать об этом.

### nginx

- `server_name _;`, отдача по IP
- `/` — статичная заглушка
- панели по **неочевидным путям** (3x-ui генерирует `webBasePath` сам)
- `limit_req` на пути панелей — вместо fail2ban
- заглушка: своя страница на 20 строк. Готовые шаблоны
  (`learning-zone/website-templates` и подобные) не нужны — заглушка
  больше не участвует в маскировке VPN, ей достаточно не быть голой
  админкой. Если всё же брать готовый — пинить коммит, `--depth 1`,
  скопировать один шаблон и удалить остальное, убрать внешние CDN
  и Google Fonts, вычистить комментарии с именем шаблона.

## 9. Шаг 5 — первый инбаунд (VLESS Reality)

**VLESS + TCP + Reality**, порт 443, создаётся через API 3x-ui
(логин по cookie, затем `panel/api/inbounds/add`).

| Параметр      | Значение                                    |
|---------------|----------------------------------------------|
| flow          | `xtls-rprx-vision` — обязательно             |
| security      | `reality`                                    |
| dest          | `127.0.0.1:8444` — локальный fakesite, см. ниже |
| serverNames   | правдоподобный домен (SNI), см. ниже         |
| fingerprint   | `firefox` — см. ниже                        |
| shortId       | генерируем                                   |
| spiderX       | `/`                                          |
| allowInsecure | **не ставить**                               |

`allowInsecure` для Reality бессмысленен. Fingerprint **не рандомизировать** —
случайные `ios`/`android`/`qq` дают неправдоподобные комбинации.

**Fingerprint — `firefox`, не `chrome`.** Первая версия ставила `chrome`
как самый распространённый uTLS-отпечаток. На практике на реальном
мобильном операторе это дало «хэндшейк проходит, трафик не идёт»:
методичный перебор параметров ссылки (SNI, xver, allowInsecure,
заглушка, длина shortId — всё исключено) показал, что решает именно
`fp`. Chrome как раз потому, что самый массовый, и оказался наиболее
сигнатурно отслеживаемым — под него DPI пишет правила в первую очередь.
`firefox` при тех же остальных параметрах работает. Значение
синхронно в `install-vpn.sh` (инбаунд) и `setup.sh` (ссылка); если
firefox тоже начнёт резать — пробовать `safari`/`ios`.

### dest — локальный fakesite, не внешний сайт

**Изначально dest был внешним реальным сайтом** (см. §11 — там же лежит
история пересмотра этого решения). На практике это оказалось критичным
багом, не просто субоптимальным выбором: REALITY на **каждое** входящее
TCP-соединение синхронно дозванивается до `dest`, ещё до чтения
ClientHello клиента (`github.com/xtls/reality`, `tls.go`, `func Server`:
`target, err := config.DialContext(ctx, config.Type, config.Dest)` —
самая первая строчка). На внешнем домене (`www.kth.se`, физически в
том же городе, что и сервер, сам по себе быстрый и надёжный — 10/10
прямых `curl` с этого же сервера) это давало **0 из 10** успешных
VLESS-хэндшейков подряд: сервер получал ClientHello, подтверждал TCP
ACK и не отвечал вообще ничего — зависание внутри xray уже после
`dial`, а не сетевая проблема. Тот же прогон с локальным dest —
**10 из 10**.

`install-vpn.sh fakesite-install` поднимает на хосте (не в Docker —
чтобы `127.0.0.1` совпадал с netns 3x-ui, который сидит в
`network_mode: host`) обычный `nginx` с self-signed сертификатом,
слушающий только `127.0.0.1:8444`. В firewall под него ничего не
нужно — loopback уже разрешён. Домен для SNI (`serverNames`) при этом
остаётся **произвольным правдоподобным именем** — сервер к нему не
подключается вообще, это чисто визуальная часть для стороннего
наблюдателя (тот же приём, что в проверенном рабочем скрипте
[YukiKras/vless-scripts](https://github.com/YukiKras/vless-scripts),
SelfSNI-режим).

Сертификат заглушки генерируется с `subjectAltName`
(`-addext "subjectAltName=DNS:${domain}"`), не только с CN. Старый
raw xray-core не проверяет x509-цепочку синтетического REALITY-серта, но
актуальные клиенты (sing-box, свежий xray-core, движок Happ) всё равно
гоняют `certs[0].Verify()`, а современный Go отклоняет only-CN
сертификаты («legacy Common Name field») — с CN-only заглушкой Happ
подключался, но не гонял трафик. С SAN — 13/13 подряд, наравне со
старым клиентом на том же инбаунде.

Ещё один ложный сигнал: встроенный **пинг задержки** в клиентах делает
обычный TLS-хендшейк к `IP:443` без слоя REALITY, получает self-signed
серт заглушки и показывает «ошибка TLS-рукопожатия» — при рабочем
проксировании. Диагностировать VLESS только по реальному трафику.

Требования к домену для SNI — чисто косметические, никакой сетевой
проверки больше не делаем (раньше был `xray tls ping`, вырезан — не к
чему стало проверять сеть, если мы по ней и не ходим):

- крупный, всегда живой HTTPS-сайт на TLS 1.3
- **не заблокирован в стране клиента** — иначе VPN на вид тоже
  «заблокирован»; домен под баном брать нельзя
- не из подборок «лучшие dest для Reality» — по инерции от старого
  подхода, но visual-часть та же самая эвристика: не хочется совпадать
  с тысячами других серверов

`setup.sh` держит встроенный пул таких доменов (`SNI_POOL` в начале
скрипта: `www.microsoft.com`, `www.apple.com`, `dl.google.com`,
`www.cloudflare.com`, `cdn.jsdelivr.net` и т.д.). Промпт на «Шаг 5»
подробно объясняет, что такое SNI; **Enter выбирает случайный домен из
пула** — если у всех серверов один и тот же SNI, это лишний признак для
DPI. Свой домен — `--sni <domain>` или ввод в промпте. Значение
фиксируется в `state.env`: сменить потом = переделывать все розданные
клиентские ссылки.

### Подписка 3x-ui

Включается автоматически (`install-vpn.sh xui-enable-sub`). Домена нет,
поэтому и панель, и подписка живут на `:8443` за nginx:

- sub-сервер 3x-ui слушает `0.0.0.0:<SUB_PORT>` (панель — `<XUI_PORT>`),
  оба порта **случайные** (20000–60000, генерятся на шаге firewall,
  фиксируются в `state.env`) — дефолтные `2053`/`2096` 3x-ui считает
  «широко известными» и ругается в своей панели. Оба закрыты в nftables,
  доступны только с docker-интерфейсов; nginx проксирует их на `:8443`
  по неочевидным путям `/sub-<hex16>/` и `/json-<hex16>/`. Значения
  тредятся через `nftables-apply`, `xui-configure`, `xui-enable-sub`,
  `render-nginx`; `0` в аргументе = «не задан», fallback на `2053`/`2096`.
- `subURI` в настройках 3x-ui — полный базовый URL с путём и слэшем;
  3x-ui дописывает к нему `subId` клиента.
- инбаунду проставляется `externalProxy` на публичный IP:443 — иначе
  в host-режиме в ссылки/подписку попадает адрес источника запроса
  (172.x от nginx-прокси), а не внешний IP.
- первому клиенту `vless-create` ставит `subId`, и сводка печатает
  готовый рабочий URL подписки.
- nginx для sub- и панельного `location` шлёт `Host $http_host` (не
  `$host` — тот срезает `:8443`) и `X-Forwarded-Proto`: из них 3x-ui
  собирает абсолютные URL (ссылки клиентов, `Profile-Web-Page-Url`, QR).
  См. журнал ниже и [`MHSanaei/3x-ui#3289`](https://github.com/MHSanaei/3x-ui/issues/3289).

Кнопка «копировать» и QR в панели 3x-ui v3.4.2 строят ссылку как
`subURI + subId`, поэтому при заполненном `subURI` дают корректный
полный URL. Тот же URL печатается в сводке; для новых клиентов —
`subURI + subId` вручную.

## 10. Шаг 6 — сводка

Собирается по ходу. В конце скрипт:

1. пишет её в `install/.state/<ip>/summary.txt` (для идемпотентности/tooling);
2. копирует в `~/ovpn-stack-<ip>-summary.txt` — чтобы не искать в `.state/`;
3. копирует приватный ключ в `~/.ssh/` (см. ниже);
4. **печатает целиком в терминал** между разделителями;
5. печатает QR первого VLESS-ключа с подписью, что он для VLESS-клиентов.

Содержит:

- адрес и путь каждой панели, логины и пароли
- команда подключения: `ssh -p <порт> <user>@<ip>` (или с `-i`, если ключ
  лёг под нестандартным именем — см. ниже)
- ссылка на первый VLESS-ключ (+ QR)
- URL подписки первого клиента (обычной и JSON) + схема для новых
- раскладка портов
- напоминание про ночной ребут в 04:00
- напоминание, что при потере доступа остаётся только консоль в панели
  управления сервером

Оба файла сводки — `chmod 600`. `install/.state/` в `.gitignore`;
домашняя копия лежит вне репозитория.

### Ключ в `~/.ssh` — чтобы клон был не нужен

Приватный ключ генерируется один раз и живёт **только** в
`install/.state/<ip>/id_ed25519` (в `.gitignore`, заново не создаётся). А
на сервере после хардненинга нет ни `root`, ни входа по паролю. То есть
удаление клонированного репозитория без копии ключа = **потеря доступа**
(остаётся только консоль провайдера).

Поэтому на «Шаге 6» скрипт по умолчанию копирует **только файл ключа**
(`chmod 600`) и `.pub` в `~/.ssh`:

- если `~/.ssh/id_ed25519` свободен (или там уже этот же ключ — сверка
  по `cmp` pub-файлов) — кладёт туда. `ssh` перебирает дефолтные имена
  сам, поэтому команда в сводке без `-i`: `ssh -p <порт> <user>@<ip>`;
- если там уже **чужой** личный `id_ed25519` — перезаписывать нельзя,
  кладёт в `~/.ssh/ovpn-stack-<ip>`, и команда в сводке с `-i`
  (нестандартное имя `ssh` сам не подхватывает без агента/`~/.ssh/config`).

После этого каталог `install/.state/` можно удалять.

`~/.ssh/config` скрипт **не трогает** — это личный файл пользователя;
удобный алиас (`Host …`) заводится вручную, если нужно. `state.env`
(пароль sudo, пароли панелей) в `~/.ssh` тоже не копируется — он в
`.state/` и в тексте сводки.

Флаг `--no-key-copy` отключает копирование — тогда ключ остаётся только
в `.state/` и удалять этот каталог нельзя.

## 11. Принятые решения и отвергнутые варианты

Записано, чтобы не возвращаться к этим вопросам через полгода.

**fail2ban — не ставим.** Пароли SSH отключены, перебор ключей невозможен.
Панели за неочевидными путями на нестандартном порту. На 443 он не просто
бесполезен, а вреден: неаутентифицированный трафик мы намеренно проксируем
на внешний сайт, и любое другое поведение выдаёт нас. Вместо него —
`limit_req` в nginx. Пересмотреть, если панель окажется на стандартном
пути или вернётся парольный SSH.

**Самоподписанная локальная заглушка как dest — сначала отвергнута,
потом принята обратно.** Первая версия этого документа отвергала схему
из стороннего скрипта (локальный nginx с self-signed сертификатом) —
аргумент был в том, что активный пробинг видит непрошедший CA
сертификат и это характерный, массово ищущийся отпечаток. Вместо этого
взяли внешний реальный сайт (`www.kth.se`) как dest.

На практике внешний dest оказался не просто теоретически
неоптимальным, а **сломанным**: REALITY дозванивается до dest
синхронно на каждое соединение до чтения ClientHello (см. §9) — внешняя
сеть, даже быстрая и надёжная сама по себе, дала 0 из 10 успешных
хэндшейков подряд на реальном сервере, зафиксировано `tcpdump`
(сервер принимает ClientHello, шлёт TCP ACK и не отвечает вообще
ничего). Локальный dest тем же прогоном — 10 из 10. Тот же приём
(self-signed + `127.0.0.1`) уже используется в проверенном рабочем
скрипте [YukiKras/vless-scripts](https://github.com/YukiKras/vless-scripts)
(SelfSNI) — то есть теоретический риск обнаружения по сертификату на
практике не помешал этому подходу быть основным в независимом,
реально работающем инструменте. Надёжность подключения оказалась
важнее теоретического снижения детектируемости для личного сервера на
пару устройств.

**Заглушка с Let's Encrypt-сертификатом для dest — по-прежнему
невозможна без домена.** IP-сертификат не помогает: SNI по стандарту —
имя хоста, IP-литералы туда не кладутся, браузер при подключении к
голому IP SNI вообще не отправляет. IP в `serverName` — сама по себе
аномалия. Именно поэтому SNI-домен остаётся вымышленным именем, а не
чем-то, для чего был бы нужен настоящий сертификат.

**3x-ui вместо голого Xray — осознанный размен.** Тяжелее (Go-демон, SQLite,
веб-морда, API), но даёт полигон: несколько инбаундов параллельно,
переключение клиентов, тест новых протоколов без сноса рабочего. При том,
что протоколы регулярно закрывают, это важнее лёгкости.

**3x-ui запинена на v3.4.2 (образ-тег, не `latest`).** В нём xray-core
26.6.27. Бамп на v3.6.0 протестирован и **отложен**: там xray 26.7.28
ставит дефолтный `minClientVer` REALITY v26.3.27, инбаунд начинает
резать клиентов со старым ядром (0/5 против 5/5 на v3.4.2), а
Go-генератор конфига в v3.6.0 выкидывает `minClientVer`, даже если
прописать его в БД руками. Разбор — журнал ниже. (Прежняя версия
заметки называла xray 25.8.29 и регрессию `MHSanaei/3x-ui#5922` —
уточнено чистыми прогонами.)

**SSH-туннель к панели — отвергнут** (неудобно с телефона).
**Панель только через VPN — отвергнута** в пользу IP-сертификата.

**Отдельный репозиторий — не нужен.** Установщик знает про этот
`docker-compose.yml`, эти шаблоны nginx, этот ovpn-admin. Отдельно —
значит синхронизировать вручную.

**`~/.ssh/config` установщик не редактирует.** Промежуточная версия
копии ключа писала туда блок `Host ovpn-stack-<ip>` по маркерам — по
требованию владельца оставили только копию файла ключа. Личный файл
пользователя; алиас заводится вручную.

## 12. Что проверить на тестах

Три вещи не проявятся сами и всплывут потом:

1. **Продление сертификата.** Срок 6 дней — проблема вылезет на седьмой,
   когда всё уже закрыто и забыто. Прогнать принудительное продление
   с релоадом nginx **прямо в установке**.
2. **Ночной ребут.** Один принудительный ребут в конце установки: всё ли
   поднялось само, не потерялись ли правила nftables, стартовал ли
   Docker раньше монтирования volume.
3. **Потеря volume.** Пересоздать контейнеры и убедиться, что клиенты
   и ключ Reality на месте.

Плюс: поведение `acme.sh` с IP-сертификатами на Debian 13 — фича свежая.

**Проверка «443 свободен» не должна ломать доустановку.** При повторном
прогоне порт занят нашим же 3x-ui. Проверять не «свободен», а «свободен
или занят нашим контейнером».

## 13. Открытые вопросы

- Git Bash на Windows без WSL: теоретически рабочий вариант, но нужны
  `.gitattributes` (LF для `*.sh`) и замена `/dev/tcp`-проверки порта
  (в MSYS-сборке bash отключена). Не тестировался — путь под Windows
  сейчас WSL2 (§1).
- Полная возобновляемость установки (сохранение состояния и продолжение
  ровно с прерванного места). Сейчас прогон идемпотентен и повторный
  запуск продолжает с нужного шага, но отдельного «чекпоинта» нет.
  Актуально для запуска с телефона через Termux: Android усыпляет
  процессы, а в середине — ребут сервера.
- Пропускать `nftables-apply` + `sshd-harden` на повторном прогоне,
  если ruleset и порт не менялись (сейчас гоняются каждый раз).

## 2026-09-06 — панель ovpn-admin показывает id контейнера; 3x-ui ругается на порт

Два косметических замечания из панелей после чистого прогона на

`sysinfo.go` → `serverName()` пробует env `OVPN_SERVER_NAME` → файл

виден IP сервера.

**3x-ui, «Предупреждения безопасности»: порт 2053 широко известен.**
Панель (`webPort`) и sub-сервер (`subPort`) на дефолтных `2053`/`2096`.

## 2026-09-06 — после харднинга остался вход по паролю (cloud-init)

Коллега прогнал установку начисто: всё работает, но по SSH к
sudo-пользователю **по-прежнему пускало по паролю**, хотя drop-in
`99-ovpn-stack.conf` ставил `PasswordAuthentication no`.

Причина — порядок чтения конфигов sshd. `/etc/ssh/sshd_config` на Debian
начинается с `Include /etc/ssh/sshd_config.d/*.conf`, файлы читаются в
алфавитном порядке, и для `PasswordAuthentication` (как и большинства
директив) выигрывает **первое** вхождение. Образ провайдера с cloud-init
кладёт `/etc/ssh/sshd_config.d/50-cloud-init.conf` со строкой
`PasswordAuthentication yes` — она идёт раньше `99-ovpn-stack.conf`, наш
`no` не применяется. `Port` и `PermitRootLogin` при этом сработали
(конкурирующих строк раньше по списку не было), поэтому проблему не
заметили: коллега зашёл на новый порт по ключу и решил, что всё ок.

Фикс (`cmd_sshd_harden`):
- drop-in переименован в `00-ovpn-stack.conf` — читается первым, наш
  `PasswordAuthentication no` побеждает cloud-init;
- дополнительно скрипт проходит по `/etc/ssh/sshd_config` и всем
  `sshd_config.d/*.conf` и комментирует `PasswordAuthentication yes` /
  `KbdInteractiveAuthentication yes` / `ChallengeResponseAuthentication
  yes` / `PermitRootLogin yes` (с бэкапом, идемпотентно);
- после рестарта — `sshd -T` как авторитетная проверка эффективного
  конфига; если `passwordauthentication` всё ещё `yes`, в лог печатаются
  конкурирующие строки;
- `sshd-rollback` сносит и `00-`, и старый `99-`, и восстанавливает
  тронутые sed-ом конфиги из свежего `.bak`.

Старое имя `99-ovpn-stack.conf` с прошлых установок удаляется при
харднинге и откате.

## 2026-09-06 — «неправильные ссылки на подписки» = баг nginx `$host`

Проверено на живом `REDACTED-IP` (3x-ui v3.4.2, `ghcr.io/mhsanaei/3x-ui:v3.4.2`)
curl'ом по реальным эндпоинтам + чтением `x-ui.db` и `docker logs` nginx.

### Что оказалось на самом деле

Раньше NOTES утверждали, что QR/«копировать» в панели за прокси на `:8443`
«склеивают URL без пути». **Это не воспроизвелось.** В v3.4.2 фронтенд
(`frontend/src/pages/clients/SubLinksModal.tsx`, `ClientQrModal.tsx`) строит
ссылку клиента буквально как `subURI + subId`, и показывает её только если
`subURI` непустой. Пока `xui-enable-sub` прописывает `subURI` (полный
`https://<ip>:8443<subPath>`), кнопка и QR дают корректный полный URL.

Реальная поломка — в другом: 3x-ui собирает **абсолютные** URL (ссылки в
самой подписке, заголовок `Profile-Web-Page-Url`, request-derived база в
`SubService.ResolveRequest` / `BuildURLs`) из заголовка `Host` запроса и
`X-Forwarded-Proto`. Живой `nginx.conf` слал `proxy_set_header Host $host`,
а `$host` **срезает порт**. Результат по curl:

    Profile-Web-Page-Url: https://REDACTED-IP/sub-.../<subId>   ← без :8443

то есть ссылка на страницу подписки указывала на `:443` (REALITY-заглушка).
С `Host: <ip>:8443` вручную заголовок сразу правильный. Панельный `location`
к тому же не слал `X-Forwarded-Proto` → scheme мог выйти `http`.

Апстрим-обсуждение и рекомендация — [`MHSanaei/3x-ui#3289`](https://github.com/MHSanaei/3x-ui/issues/3289)
и доки [Reverse Proxy](https://docs.sanaei.dev/docs/operations/reverse-proxy/):
`Host $http_host`, `X-Forwarded-Proto`, проброс `Range`/`If-Range`.
`proxy_redirect off` из того обсуждения **не берём** — там `proxy_pass`
без пути + `rewrite`, а у нас `proxy_pass` с базовым путём, где default
`proxy_redirect` как раз нужен, чтобы не утёк upstream-хост в `Location`.

### Фикс (в этом коммите)

`templates/nginx.conf.tmpl`, все `location` секций VLESS + OpenVPN:
- `Host $host` → `Host $http_host` (сохраняет `:8443`);
- `X-Forwarded-Proto $scheme` добавлен в панельный и ovpn-admin блоки;
- `Range`/`If-Range` проброшены в sub- и json-sub-блоки.

Проверено на живом сервере: до фикса `curl` подписки отдавал
`Profile-Web-Page-Url: https://REDACTED-IP/sub-…` (без порта), после
патча `Host $http_host` + reload nginx — `https://REDACTED-IP:8443/sub-…`.

Сам контент подписки был корректен и до фикса: `externalProxy` даёт
`vless://…@<public_ip>:443`, `fp=firefox`, `pbk`/`sid`/`sni` на месте;
Happ на Android тянул подписку с кодом 200 (видно в `docker logs nginx`).

### Решили ли это в свежих 3x-ui? — Нет, механизм тот же

v3.5 → v3.7 (v3.6.0 «Subscription Correctness»). `SubService.ResolveRequest`
всё так же строит абсолютные URL как `X-Forwarded-Host || Request.Host` +
`X-Forwarded-Proto`. То есть nginx с `Host $host` (без порта) даёт кривой
URL и на v3.7 — лечится только `$http_host`, либо `X-Forwarded-Host` с
портом, либо `subURI`. Кнопка/QR в панели по-прежнему `subURI + subId`.

Что **добавили** в v3.6.0 (PR #6135, `internal/sub/forwarded_trust.go`):
настройку **`trustedProxyCIDRs`** (дефолт `127.0.0.1/32,::1/128`). Если её
увести от дефолта, 3x-ui доверяет `X-Forwarded-*` только когда
`RemoteAddr` прокси попадает в эти CIDR, иначе **игнорирует** форвард-хедеры
и берёт хост запроса + пишет варнинг («set subURI, or add the proxy…»).
Пока значение = дефолту, хедеры принимаются от кого угодно (обратная
совместимость). **Для нас:** nginx-контейнер стучится к host-mode 3x-ui с
адреса docker-моста (172.x), не с loopback. Если когда-нибудь тронем
`trustedProxyCIDRs` — вписать туда `172.16.0.0/12` (или просто
полагаться на `subURI`, он у нас и так выставлен).

Прочие sub-фиксы v3.6.0 (Clash YAML-скаляры, VLESS flow в JSON, дубль
fingerprint в externalProxy tlsSettings, имена внешних ссылок) — общая
корректность, нашей проблемы не касаются.

## 2026-09-05 — телефон не подключался по VLESS

Диагностика велась на тестовом сервере `REDACTED-IP` (Debian 13),
сравнением с эталонным `YukiKras/vless-scripts` 3x-ui на том же IP.

### Три причины, все в установщике, все пофикшены

1. **Пустой `pbk` в ссылке (парсинг `xray x25519`).**
   `install-vpn.sh` доставал публичный ключ через `grep 'Public'`.
   xray-core ≥ 25.x (в запиненной 3x-ui v3.4.2 это xray 25.8.29)
   переименовал строку вывода в `Password:`. `pub` выходил пустым,
   ссылка уходила с `pbk=` пустым, REALITY не аутентифицировался.
   Фикс: матчим `password|public`, валидируем 43-символьный base64url.
   Коммит `473fd6f`.

2. **`fp=chrome` режется мобильным оператором.**
   С валидным `pbk` хэндшейк проходил (`XtlsPadding`/`splice` в логе
   клиента), но трафик не шёл — `dial ... operation was canceled`.
   Побайтовый перебор параметров ссылки против рабочего YukiKras:
   SNI (`<ip>.sslip.io` vs случайный `.ru`), `xver`, `allowInsecure`,
   контент заглушки, длина `shortId` — **всё исключено**. Решает `fp`:
   `chrome` (самый массовый uTLS-отпечаток → наиболее сигнатурно
   отслеживаемый DPI) не работает, `firefox` при прочих равных —
   работает. Дефолт сменён на `firefox` в `install-vpn.sh` и `setup.sh`.
   §9 раньше советовал `chrome` — логика инвертировалась.
   Коммит `43dcc02`. **Замечание:** это, возможно, специфично для
   конкретного оператора; если `firefox` тоже начнёт резать — пробовать
   `safari`/`ios`, значение в `cmd_vless_create`, локальная переменная.

3. **Ссылки из панели 3x-ui — с пустым `pbk`.**
   `streamSettings` инбаунда содержал `realitySettings.privateKey`, но
   не `realitySettings.settings.publicKey`. xray на инбаунде это поле
   игнорирует, а 3x-ui читает ИМЕННО его при построении клиентских
   ссылок/QR/подписки. Любая ссылка, созданная через панель (второй
   клиент, перегенерённый QR), уходила с `pbk=` пустым.
   Фикс: пишем `settings.{publicKey,fingerprint,serverName,spiderX}`.
   Коммит `63bf3be`.

### Happ — это xray-core, не sing-box

README раньше писал «sing-box (Happ)». Happ использует xray-core для
прокси, sing-box — только для TUN-режима. Есть форк `Happ-proxy/Xray-core`.

### «Ошибка TLS-рукопожатия» во встроенном пинге клиента

Тест задержки в Happ/др. делает обычный TLS-хендшейк к `IP:443` с SNI,
без слоя REALITY → получает self-signed сертификат fakesite → «ошибка».
Это норма, не поломка. Диагностировать VLESS только по реальному трафику.

### Подписка 3x-ui (добавлена как фича, ветка feat/subscriptions)

Изначально не поддерживалась. Что сделано:
- `bootstrap.sh` — nftables пускает `2096` с `docker0`/`br-*` (как `2053`).
- `nginx.conf.tmpl` — `location` для `@@SUB_PATH@@` и `@@SUB_JSON_PATH@@`
  → `host.docker.internal:2096`.
- `install-vpn.sh xui-enable-sub` — правит `x-ui.db` напрямую (флагов
  в `x-ui setting` нет, panel-API требует CSRF): `subEnable`,
  `subPort=2096`, `subPath`/`subJsonPath` рандомные, `subURI` =
  полный базовый URL с путём.
- `vless-create` — `externalProxy` на `<public_ip>:443` (иначе адрес
  в подписке = `172.x` от прокси); первому клиенту ставит `subId`.
- `setup.sh` — генерит пути, прокидывает, печатает URL подписки в сводку.

**~~Ограничение~~ (снято):** здесь раньше стояло, что QR/«копировать» в
панели за прокси на `:8443` дают битый URL без пути. Это оказалось
неверно — см. запись «2026-09-06 — неправильные ссылки на подписки».
Реальная поломка была в `Host $host` в nginx (срезал `:8443`);
исправлено на `$http_host` (коммит `a7863ac`). QR и кнопка «копировать»
в панели строят `subURI + subId` и дают корректную полную ссылку.

### Идемпотентность прогонов — ПОФИКШЕНО (2026-09-06)
